# Проектная записка: взвешенная бинарная кросс-энтропия для положительного класса

> Тип: Design Note. Предложение нового закрытого оператора функции потерь для
> редких бинарных событий. Не определяет действующее поведение, сетевую схему
> или реализацию Transformer.

- Статус: к межпроектальному обсуждению
- Срез: 2026-09-24; техническая исходная точка — Semantic v3 и Flight v16
- Инициатива: контролируемый A/B без дублирования строк, повторной выборки
  или скрытой интерпретации непрозрачной идентичности цели

## 1. Проблема

Semantic v3 содержит `BinaryCrossEntropyWithLogits`. Этот оператор принимает
конечные целевые значения из закрытого интервала `[0, 1]`; в том числе он
намеренно допускает дробные метки. Его поле `weight` — вес всего прямого
компонента в `WeightedSum`, а не вес положительного класса.

Для эксперимента с редким строго бинарным событием нужен отдельный оператор.
Нельзя добавить `positiveClassWeight` к старому
`BinaryCrossEntropyWithLogits`: даже при `positiveClassWeight = 1` это изменило
бы его допустимую область и лишило бы старый оператор поддержки дробных меток.

Эта записка предлагает форму следующей семантической ревизии, правила проверки,
публичную проекцию и переход. До выпуска канонического пакета действующие
Semantic v3 и Flight v16 не меняются.

## 2. Предлагаемый оператор

Точное имя нового прямого оператора:

```text
PositiveClassWeightedBinaryCrossEntropyWithLogits
```

Он является отдельным вариантом прямого компонента. Его концептуальная
декларация имеет вид:

```json
{
  "identity": "direct.opaque-event",
  "operator": "PositiveClassWeightedBinaryCrossEntropyWithLogits",
  "weight": 1,
  "positiveClassWeight": 28,
  "targetIdentity": "Opaque.Event"
}
```

`positiveClassWeight` обязателен, является конечным числом IEEE-754 binary64
и строго больше нуля. Значения по умолчанию нет: базовый вариант A/B явно
передаёт `1`, а взвешенный — выбранное вызывающей системой значение, например
`28`. Transformer не выводит его из состава строк, идентичности цели, метки
модели, профиля, FIGI либо иной внешней предметной семантики.

Поле `weight` сохраняет действующую роль: оно умножает готовое среднее прямого
компонента в `WeightedSum`. `positiveClassWeight` действует только на
слагаемое положительного класса каждой бинарной строки. Это две независимые
семантики.

Старый `BinaryCrossEntropyWithLogits` сохраняется без изменения. Он остаётся
подходящим для бинарных и дробных целевых значений в `[0, 1]` и не принимает
новое поле.

## 3. Математическая семантика

Для исходного логита `z`, строго бинарного наблюдения `y` и
`w = positiveClassWeight` потеря одной строки равна:

```text
L(z, y) = -w * y * log(sigmoid(z))
          - (1 - y) * log(1 - sigmoid(z))
```

Transformer вычисляет эту функцию непосредственно по логитам численно
устойчивым способом. Реализация через предварительное `sigmoid(z)` и затем
логарифмы недопустима для предельных логитов. Внутренний dtype тензора и
конкретный API PyTorch принадлежат Transformer.

Порядок агрегации фиксирован:

```text
directMean = GlobalRowMean(L(z_i, y_i))
directContribution = component.weight * directMean
totalLoss = WeightedSum(directContribution, auxiliaryContributions)
```

Делитель `GlobalRowMean` — число всех строк, а не сумма весов классов. При
`w = 1` функция потерь совпадает с обычным BCEWithLogits на бинарной области.

Публичная вероятность всегда выводится из того же `positiveClassWeight`:

```text
q = sigmoid(z - log(w))
```

Это обратная поправка только к искусственному взвешиванию положительного
класса в функции потерь. `q` — вероятность для невзвешенного распределения,
представленного данным набором строк, при обычной интерпретации условного
правдоподобия модели. Это не обещание общей статистической калибровки,
качества вне набора данных или обобщающей способности.

## 4. Допустимость декларации и входных значений

Оператор допустим только для прямого компонента, если его соответствующий слот
цели одновременно удовлетворяет всем условиям:

- `observedConstraint` — ровно `ClosedInterval` с minimum `0` и maximum `1`;
- `lossInputTransformation` — `Identity`, то есть функция потерь получает
  исходные логиты;
- `publicPredictionTransformation` — `Sigmoid`;
- цель не используется ни в одной роли вспомогательного компонента.

Последнее правило относится ко всем вспомогательным ролям, включая
`GaussianNLL`, `ExpectedValue` и `RiskAdjustedExpectedValue`. В первой
ревизии взвешенная бинарная цель не участвует во вспомогательном графе. Это
исключает неявную смену семантики их входов со взвешенной оценки на исправленную
вероятность.

Каждое фактическое `y` для такого слота обязано после чтения Arrow Float32 быть
ровно `0` либо `1`; `-0.0` семантически равно `0`. Проверка выполняется
дважды:

1. при приёме каждого DoPut payload для `fit`;
2. при повторном чтении подтверждённых Arrow-артефактов Worker-ом, включая
   recovery внутри работающего сервиса.

Старый `BinaryCrossEntropyWithLogits` этой проверкой не затрагивается и
сохраняет поддержку дробных меток.

## 5. Структурированные результаты проверки

Следующая семантическая ревизия сохраняет разделение структурной схемы,
семантической проверки, проверки входных значений, совместимости и повреждения
сохранённых данных. Предлагаемая публичная модель ошибок:

| Ситуация | Код / причина | Обязательные данные |
| --- | --- | --- |
| Поле `positiveClassWeight` отсутствует, нечисловое или `<= 0` | `INVALID_ARGUMENT / INVALID_OBJECTIVE` | JSON Pointer на поле |
| `positiveClassWeight` не является конечным JSON number | `INVALID_ARGUMENT / INVALID_MODEL_CONTRACT` | JSON Pointer на поле |
| Оператор применён не к прямому компоненту, к неподходящему слоту либо цель участвует во вспомогательной роли | `INVALID_ARGUMENT / INVALID_OBJECTIVE` | JSON Pointer на `operator`, слот или роль |
| Во входе `fit` встретился `y`, отличный от `0` и `1` | `INVALID_ARGUMENT / TARGET_VALUE_INVALID` | `targetIdentity`, `targetIndex`, `logicalRow`, `expectedDomain: "Binary"` |
| Сохранённые метаданные содержат противоречивый оператор или выводимую проекцию | `MODEL_CORRUPT / STORED_CONTRACT_INVALID` | layer и JSON Pointer |
| Тёплый старт сравнивает разные objective/model identities | `MODEL_SCHEMA_MISMATCH / DIGEST_MISMATCH` | layer `objective` либо `model`, expected и actual SHA-256 |
| Исполнение получает неконечное исходное значение или не может выпустить конечный публичный результат | существующий результат исполнения для неконечного значения | `path` и диагностическое сообщение Transformer |

Текст сообщения не является API. Вызывающая система ветвится по `code`,
`reason` и структурированным полям.

## 6. Публичная проекция, принадлежащая checkpoint-у

Поправка не является отдельной декларацией, не передаётся вызывающей системой
и не выбирается независимо от `positiveClassWeight`. Единственный источник
этой семантики — прямой компонент с
`PositiveClassWeightedBinaryCrossEntropyWithLogits`.

После проверки Transformer разрешает описание предсказания, принадлежащее
checkpoint-у, для соответствующей цели. Оно однозначно сообщает, что
публичный результат предсказания равен `q = sigmoid(z - log(w))`, и показывает
фактическое `positiveClassWeight`. Точное JSON-представление этой выданной
Transformer проекции будет определено только в стадийном каноническом пакете.

Требования к публичным поверхностям:

- `predict.create` возвращает такое описание для выбранного `modelRef`, а не
  только literal `Sigmoid`;
- `Model Catalog detail` возвращает точный ModelContract и разрешённое описание
  предсказания, достаточное для интерпретации выхода без повторного расчёта
  поправки к логиту вызывающей системой;
- `Model Topology` показывает отдельный выводимый узел поправки между исходным
  логитом и публичной вероятностью после Sigmoid, с relation
  `-log(positiveClassWeight)`;
- `Training Telemetry` считает MAE, RMSE и другие метрики цели по исправленной
  публичной вероятности. `directLosses`, `selectionScore` и `totalLoss`
  остаются наблюдениями взвешенной целевой функции обучения.

`Model Topology` не раскрывает параметры, устройство, tensor layout либо
значение private resource. `positiveClassWeight` уже является явной
семантической декларацией и может быть показан как свойство соответствующего
узла прямой функции потерь.

## 7. Идентичность и совместимость

В переходе с Semantic v3 на v4 изменяются оба D1-дайджеста target и objective,
даже если их документы совпадают по содержанию: в предобраз входит revision
языка. Внутри Semantic v4 изменение только `positiveClassWeight` меняет
`objectiveSha256`, а вслед за ним выданный Transformer `modelDefinitionSha256`.
Отдельный дайджест поправки или хеширование, независимое от представления, не
нужны.

Внутри Semantic v4 изменение только `positiveClassWeight` не меняет
`targetContractSha256`: выводимая поправка принадлежит связке слота цели с
новым прямым компонентом. Literal `Sigmoid` остаётся декларацией конечной
связи, а точная формула над исходным логитом принадлежит разрешённому описанию
предсказания. Полная совместимость всё равно точна, поскольку описание модели
связывает objective identity и разрешённую конфигурацию Transformer.

Новое поколение модели не совместимо для тёплого старта с поколением, у
которого отличается оператор или `positiveClassWeight`. Существующие модели
Semantic v3 не переинтерпретируются как взвешенные бинарные модели.

## 8. Публикация ревизий

Предлагаемый набор будущих ревизий:

| Пакет | Предлагаемая ревизия | Причина |
| --- | --- | --- |
| Семантический язык | v4 | Новый закрытый прямой примитив, бинарная область входов, D1 и capabilities. |
| Flight | v17 | Закрытые схемы `fit`/`predict` v16 ссылаются на Semantic v3 и не выражают разрешённую проекцию. |
| Model Catalog | v4 | Detail возвращает Semantic v4 ModelContract и описание предсказания. |
| Model Topology | v2 | Граф должен явно показать выводимую поправку. |
| Training Telemetry | v4 | Метрики эпох получают смысл исправленной публичной вероятности для модели Semantic v4; массивы JSON могут остаться прежней формы. |
| Worker | v15 | Command manifest и проверка исполнения принимают Semantic v4. |
| Checkpoint/recovery | v9 | Метаданные связывают новый ModelContract и описание предсказания. |
| Metrics и fit-run | v8 | Записи телеметрии Transformer принадлежат generation Semantic v4. |

Это предложение согласованного чистого перехода. Flight v17 не обслуживает
Semantic v3 формы `create`/`predict` и не принимает псевдонимы. Если решение
сохраняет отсутствие модуля чтения Semantic v3, развёртывание удаляет
существующие опубликованные поколения, checkpoints, незавершённые jobs и старую
телеметрию после перехода jobs в terminal state. Модели обучаются заново;
конвертация weights и устаревший reader не предусматриваются.

До отдельного решения о чистом переходе ни удаление существующих данных, ни
миграция, ни изменение исполнения не выполняются.

## 9. Возможности, проверочные примеры и контролируемый A/B

Semantic v4 capabilities явно рекламируют
`PositiveClassWeightedBinaryCrossEntropyWithLogits` и его binary-only domain.
Flight v17 capabilities объявляют согласованные ревизии запросов. В
capabilities не появляются названия целей, имена профилей или предметные правила.

Стадийный канонический пакет должен содержать как минимум:

- допустимые документы с `positiveClassWeight: 1` и `28`;
- отрицательные случаи для дробной метки, нуля, отрицательного и неконечного
  weight, неподходящего слота и любой вспомогательной роли;
- числовые векторы для положительной и отрицательной меток, `w = 1`, `w = 28`
  и предельных конечных логитов;
- JCS/D1 векторы, доказывающие изменение objective/model identities при
  изменении weight;
- проверочные примеры `fit.create`, `predict.create`, Catalog detail, Topology
  и Telemetry;
- проверку, что публичный output при `w = 28` равен `sigmoid(z - log(28))` с
  нормативно заданной численной погрешностью, а не взвешенной оценке
  `sigmoid(z)`.

Эталонные векторы не требуют побайтового совпадения внутренних CUDA
вычислений. Они фиксируют математическую формулу, редукцию и допустимую
числовую погрешность на публичной границе Float32.

Контролируемый A/B сохраняет зафиксированный Arrow-артефакт, порядок строк,
настройки модели, initialization, seed, детерминированный режим, AMP policy,
optimizer и training configuration. Отличается только
`positiveClassWeight`. Сопоставимыми результатами служат невзвешенный BCE,
PR-AUC, Brier и метрики исправленной публичной вероятности; абсолютные
`totalLoss` и `directLosses` между A и B не являются сравнительной метрикой
качества.

## 10. Вне scope

Предложение не включает:

- автоматический подбор weight из загруженного набора данных;
- дублирование строк, повторную выборку или иную скрытую политику выборки;
- изменение формулы существующего `BinaryCrossEntropyWithLogits`;
- диагностику параметров целевой головы;
- утверждение о статистической калибровке или обобщающей способности;
- ветвление Transformer по непрозрачной identity цели;
- изменение `indexedFeatureBlocks`, восстановления Arrow или физического
  формата DoPut payload.

## 11. Следующий шаг

После межпроектальной проверки Transformer выпускает стадийный канонический
пакет Semantic v4 / Flight v17 с закрытыми JSON Schemas, capabilities,
structured errors, проверочными примерами и manifest. Только после побайтно
идентичной проверки вызывающей системой допустимы реализация в коде и
разрушительный чистый переход.
