# Проектная записка: Input Snapshot v1

> Тип: Design Note. Предложение о самостоятельном жизненном цикле
> неизменяемого набора входных данных `fit`. Не определяет действующую
> реализацию, сетевую схему, CLI или контракт хранения.

- Статус: к межпроектальному обсуждению
- Срез: 2026-09-24; техническая исходная точка — Flight v16 и Semantic v3
- Инициатива: повторные `fit` на точно тех же данных без повторной
  материализации пакетов Arrow Flight вызывающей системой

## 1. Проблема

Вызывающая система материализует исходные данные в компактные пакеты Arrow
Flight и передаёт их Transformer через DoPut. Эта операция может быть
существенно дороже повторного запуска обучения.

Повторный `fit` на точном наборе данных нужен, в частности, для диагностики
схлопывания target в константу: различие между экспериментами тогда можно
отнести к настройкам модели, objective или конфигурации обучения, а не к
изменившемуся набору строк.

Существующие входные Arrow-артефакты не являются публичным механизмом
повторного использования:

- каждый файл принадлежит одному заданию и его квитанции в PostgreSQL;
- рабочий процесс проверяет квитанцию, SHA-256, схему Arrow и счётчики именно
  этого задания;
- входы `fit` находятся в хранилище `recovery` только для восстановления
  текущего задания внутри работающего сервиса;
- процедура обслуживания удаляет каталог `recovery` завершённого
  `fit`-задания;
- произвольный путь файловой системы не пересекает публичную границу и не может
  быть аргументом CLI или нового задания.

Следовательно, нельзя надёжно строить эксперимент на том, что процедура
обслуживания ещё не удалила файлы прежнего задания. Нужен отдельный
неизменяемый ресурс данных со своими идентичностью, владением и жизненным
циклом.

## 2. Цель

Предлагается `Input Snapshot v1`: неизменяемый набор завершённых входов `fit`
в области одного владельца. Он создаётся только по явному запросу при первом
`fit`, после чего может стать источником новых `fit`-заданий без DoPut.

```text
вызывающая система
    │
    │ первый fit с явным запросом сохранить Input Snapshot
    ▼
Transformer
    ├─ обычный DoPut и проверка пакетов Arrow
    ├─ неизменяемый Input Snapshot
    └─ первый fit

локальный CLI Transformer
    │
    │ inputSnapshotRef + новая конфигурация fit
    ▼
та же управляющая плоскость Transformer
    └─ новый fit без повторного DoPut
```

CLI не запускает рабочий процесс напрямую. Он создаёт задание через ту же
управляющую плоскость работающего сервиса, которая владеет планированием, CUDA,
отменой, жизненным циклом PostgreSQL, телеметрией и очисткой.

## 3. Вне scope

Input Snapshot v1 не означает:

- автоматическое сохранение входов каждого `fit`;
- передачу произвольного пути файловой системы в Transformer;
- изменение `indexedFeatureBlocks` или плоскости данных Arrow;
- перенос материализации исходных данных из Inventory в Transformer;
- повторное использование snapshot для `predict`;
- восстановление старых завершённых заданий или recovery после перезапуска
  сервиса;
- изменение формул objective, семантики target либо published-model warm start.

Snapshot не является моделью, checkpoint, отчётом телеметрии или состоянием
recovery. Он представляет только завершённый и проверенный набор входных данных
`fit`.

## 4. Текущее состояние

Каждый DoPut уже записывается Transformer как файл Arrow IPC:

1. сервис валидирует метаданные и каждый `RecordBatch`;
2. `InputUploadSession` записывает пакет во временный Arrow-файл;
3. после `fsync` сервис вычисляет SHA-256 и атомарно публикует файл;
4. PostgreSQL получает неизменяемую квитанцию с путём, дайджестом, отпечатком
   схемы и счётчиками;
5. рабочий процесс читает только такие подтверждённые артефакты и повторно
   проверяет их квитанции перед первым чтением.

Для `fit` класс хранения равен `recovery`. Это обеспечивает восстановление
после повторяемого сбоя внутри текущего задания, но не независимое хранение
данных: после перехода `fit` в завершённое состояние процедура обслуживания
очищает соответствующий каталог `recovery`. Published model также не удерживает
и не публикует свои входные артефакты.

Таким образом, существующий слой записи Arrow-файлов является подходящей
физической основой, но текущий жизненный цикл намеренно не создаёт
переиспользуемый набор данных.

## 5. Предлагаемая семантика

### 5.1 Явный запрос на сохранение

Первый `fit` явно запрашивает сохранение входных данных. Точное имя будущего
поля пока не выбирается; в этой записке оно обозначается как
`retainInputSnapshot`.

Без такого запроса текущая семантика сохраняется: входные артефакты принадлежат
заданию и очищаются согласно его жизненному циклу.

Намерение сохраняется при создании первого `fit`-задания, а не после получения
модели. Это исключает гонку с очисткой завершённого задания и ручное копирование
файлов, которыми управляет сервис.

### 5.2 Момент создания

Snapshot создаётся только после успешного `input.close`, когда Transformer уже
проверил полный упорядоченный манифест входных данных. Он может стать доступным
до завершения первого обучения: принадлежность данных не зависит от того,
удалось ли модели сойтись или опубликоваться.

Если snapshot был явно запрошен, сбой его создания не должен превращаться в
«успешный `fit` без snapshot». Задание не переходит в очередь, пока Transformer
не сможет зафиксировать полный snapshot либо вернуть структурированную ошибку
квоты, хранилища или целостности.

Неполная загрузка, прерванный вход и незакрытый манифест входных данных никогда
не создают snapshot.

### 5.3 Идентичность и состав

Transformer выпускает непрозрачный `inputSnapshotRef`. Он не является путём
файловой системы, именем модели, label или производным из внешней предметной
идентичности.

Snapshot хранит либо однозначно связывает:

- область владельца;
- неизменяемый упорядоченный манифест входных данных и его дайджест;
- каждую квитанцию пакета: ordinal, SHA-256, число байтов, отпечаток схемы,
  границы диапазонов, логические строки, chunks и native rows;
- `dataContractSha256`, `tensorGeometry` и `inputLayout`;
- точный `TargetContract` и `targetContractSha256`;
- время создания и метаданные хранения, принадлежащие Transformer.

Файлы пакетов остаются под управлением Transformer. Новый `fit` получает
snapshot только по непрозрачной ссылке; ни вызывающая система, ни локальный CLI
не читают и не передают их исходные пути.

### 5.4 Целостность при повторном `fit`

Перед запуском рабочего процесса Transformer повторно проверяет манифест
snapshot, ссылки на артефакты, SHA-256, физическую схему Arrow и счётчики.
Snapshot не ослабляет текущие проверки целостности и не превращает исходные
файлы в доверенный вход без проверки.

Новый `job` хранит собственную неизменяемую конфигурацию и собственный дайджест
конфигурации. Он ссылается на snapshot как на источник входных артефактов, но
не меняет и не переиспользует жизненный цикл исходного задания.

## 6. Совместимость повторного `fit`

Snapshot v1 предназначен для изменения поведения модели при неизменной
интерпретации входных данных.

| Свойство нового `fit` | Допустимо | Причина |
| --- | --- | --- |
| `learningRate`, `batchSize`, `epochs`, seed, AMP, selection | Да | Не меняют вход Arrow. |
| `hiddenWidth`, число encoder layers, attention heads, dropout | Да | Это настройки модели, а не геометрия входа. |
| Операторы и веса objective | Да, при точном `TargetContract` | Входные target values сохраняют прежнюю семантику. |
| `seqLen` | Нет | `observationOffsets` в Arrow имеют фиксированную длину. |
| `featureDim` | Нет | Меняется ожидаемая ширина восстановления. |
| `inputLayout.featureBlocks` | Нет | Меняется физическая схема native rows и расположение blocks. |
| Target slots, их порядок, transformations или constraints | Нет в v1 | Меняется интерпретация `tgt` values. |
| `dataContractSha256` | Нет | Snapshot связан с точной идентичностью данных. |

Иными словами, «другая геометрия» допустима только если под ней понимаются
внутренние параметры architecture. Изменение `seqLen`, `featureDim` или layout
требует новой материализации пакетов. В будущем можно отдельно рассмотреть
более низкоуровневый формат исходных данных, но он не входит в Input Snapshot
v1.

## 7. Жизненный цикл и удаление

Snapshot имеет жизненный цикл, отдельный от исходного задания и published model:

- очистка завершённого исходного задания не удаляет snapshot, на который есть
  ссылка;
- удаление published model не удаляет snapshot автоматически: один snapshot
  может использоваться несколькими поколениями моделей;
- snapshot удаляется только явной операцией в области владельца либо
  согласованной политикой хранения;
- квота и дисковый budget применяются до принятия snapshot в хранилище;
- неизвестный, чужой и удалённый `inputSnapshotRef` не раскрывают существование
  постороннего набора данных.

Подходящая внутренняя реализация — отдельный управляемый корневой каталог
хранилища и реестр записей snapshot. Transformer может использовать копирование,
жёсткую ссылку или другой безопасный механизм устранения дублирования, но эти
детали не входят в публичный контракт. Запрещено удерживать snapshot неявной
ссылкой на каталог завершённого задания.

## 8. Предлагаемый порядок работы CLI

Точный синтаксис CLI не является частью этой записки. Концептуальный порядок
работы:

```text
1. Inventory создаёт первый fit с явным запросом retainInputSnapshot.
2. После input.close Transformer выдаёт inputSnapshotRef.
3. Первый fit завершается обычным путём.
4. Оператор запускает CLI Transformer с inputSnapshotRef и новым описанием fit.
5. CLI создаёт новый job через работающий сервис Transformer.
6. Новый job получает входы snapshot, поэтому DoPut отсутствует.
```

CLI передаёт полное новое описание fit: label, device, model contract,
конфигурацию обучения, diagnostics и initialization. Data binding и target
contract он получает из snapshot и требует точную совместимость до постановки
задания в очередь.

CLI не должен:

- принимать input directory или список `.arrow` paths;
- запускать Worker вне сервиса;
- принимать произвольную идентичность владельца;
- реконструировать или изменять пакеты snapshot;
- обходить authentication, mutation lease, квоту либо scheduler.

## 9. Граница ответственности

| Область | Ответственность |
| --- | --- |
| Inventory | Один раз материализует и отправляет пакеты; явно выбирает сохранение snapshot; может хранить `inputSnapshotRef` для UI и экспериментов. |
| Transformer | Владеет реестром snapshot, файловыми артефактами, проверками целостности, областью владельца, хранением, допуском повторного использования и исполнением заданий. |
| Локальный CLI Transformer | Создаёт новое задание от snapshot через управляющую плоскость Transformer; не читает исходные входные файлы. |
| Terminal | Не получает исходные пути или Arrow bytes; может отображать ссылку snapshot только через безопасную проекцию Inventory. |

## 10. Невыбранные варианты

### Продлить хранение обычных входов задания

Не подходит: файлы остаются привязаны к завершённому заданию, не имеют
отдельной идентичности и могут быть удалены процедурой обслуживания. Такой
подход не определяет владение, совместимость и семантику удаления нового `fit`.

### Разрешить CLI путь к `.arrow`-файлам

Не подходит: это обходит квитанции PostgreSQL, область владельца, проверки
целостности и границу управляемого хранилища. Кроме того, путь не переносим
между экземплярами сервиса.

### Автоматически сохранять входы каждого `fit`

Не подходит для v1: это неявно изменяет стоимость хранения и срок удержания
всех запусков, включая одноразовые и ошибочные эксперименты.

### Поддержать новую геометрию входа поверх прежних Arrow-файлов

Не подходит: компактная схема Arrow уже кодирует `seqLen`, расположение blocks
и ширину target. Реализация означала бы новую материализацию либо новый формат
исходных данных, принадлежащий Transformer, а не повторное использование
существующего snapshot.

## 11. Версионирование и переход

Flight v16 имеет закрытый набор действий и схем. Input Snapshot v1 не должен
добавляться как скрытое поле или локальный обход текущего порядка работы.

Потребуется отдельный версионированный пакет, который определит как минимум:

- явный запрос хранения при первом `fit`;
- результат, в котором становится доступен `inputSnapshotRef`;
- создание `fit`-задания от snapshot без DoPut;
- декларацию возможностей, лимиты, квоты и структурированные ошибки;
- list/detail/delete в области владельца, если эти операции нужны в v1;
- происхождение snapshot в checkpoint/recovery и манифесте `job`;
- межъязыковые тестовые примеры для обычного, несовместимого, чужого,
  удалённого и повреждённого snapshot.

Предварительно это означает следующую ревизию протокола Flight, но точная
матрица версий Flight, Worker, checkpoint/recovery и миграции PostgreSQL должна
быть выбрана только после межпроектальной проверки канонического пакета.

Существующие завершённые задания и их текущие recovery-каталоги не
конвертируются в snapshot задним числом: файлы могли быть удалены, а у них нет
отдельного жизненного цикла snapshot. Новые snapshots появляются только после
принятия нового контракта и явного запроса.

## 12. Критерии следующей проверки

Перед каноническим пакетом должны быть согласованы следующие результаты:

1. Явно запрошенный snapshot создаётся только из полного проверенного манифеста
   входных данных и получает непрозрачный `inputSnapshotRef`.
2. Snapshot можно использовать для нескольких новых `fit`-заданий без DoPut и
   без изменения исходных артефактов.
3. Изменение конфигурации обучения, настроек модели или objective при точном
   `TargetContract` допускается.
4. Изменение data binding, target contract либо геометрии входа отклоняется до
   очереди с точной структурированной ошибкой.
5. Очистка исходного завершённого задания не удаляет snapshot; удаление snapshot
   не нарушает уже работающее задание.
6. Неизвестные, чужие и удалённые snapshot references дают одинаковый с точки
   зрения безопасности результат.
7. Повреждённый артефакт, манифест или квитанция никогда не запускает Worker.
8. Хранилище snapshot имеет явные квоту, срок удержания и безопасный путь
   удаления.

После согласования этих семантических вопросов Transformer может подготовить
поэтапный канонический пакет. До этого код, миграции, Flight v16 contracts и
адаптер Inventory не меняются.

## 13. Новая семантика CLI

CLI не работает с Arrow-файлами и путями. Он создаёт обычный новый fit, но вместо DoPut ссылается на ранее явно сохранённый
snapshot.

```sh
Первый запуск через Inventory
  └─ fit + явное «сохранить входной snapshot»
        └─ DoPut → проверка → input.close
            └─ Transformer выдаёт inputSnapshotRef

Повторный запуск через CLI Transformer
  └─ inputSnapshotRef + новая конфигурация обучения
        └─ новый job без DoPut
            └─ Worker читает те же проверенные Arrow-пакеты
```
Концептуально это выглядело бы так:

```sh
# На стороне Inventory: первый fit с явным сохранением входов.
model fit ... --retain-input-snapshot

# В результате после закрытия input:
inputSnapshotRef: inp_...

# Позже на стороне Transformer:
transformer model fit \
  --input-snapshot-ref=inp_... \
  --model-definition=... \
  --training-config=...
```

Вторая команда:

- не принимает каталог или список .arrow-файлов;
- не загружает данные повторно;
- не запускает Worker напрямую;
- создаёт новый job через работающий сервис Transformer;
- проходит те же проверки владения, квот, целостности и совместимости.

Из snapshot берутся неизменяемые данные: входная геометрия, target contract, data binding и проверенный манифест. Менять можно параметры модели и
обучения, например hidden width, число encoder layers, learning rate, batch size, epochs, AMP и diagnostics.

Менять нельзя seqLen, featureDim, структуру indexedFeatureBlocks, targets или их порядок: это уже потребовало бы новой материализации входов.

inputSnapshotRef живёт отдельно от исходного job. Повторный fit его не удаляет; удаление возможно только отдельной операцией или по согласованной
политике хранения.

Это пока проектная семантика, а не существующий CLI/API.
