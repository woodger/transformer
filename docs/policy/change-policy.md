# Политика внесения изменений

> Type: Policy. Этот документ задаёт порядок безопасного изменения проекта.

## Сначала понять систему

Перед правкой нужно проверить относящиеся к задаче:

- production-код и точки запуска;
- тесты и fixtures;
- CLI help и конфигурацию;
- документацию, ADR и нормативные contracts;
- persistence, filesystem и subprocess lifecycle.

Не следует предполагать поведение, которое можно установить по репозиторию.

## Минимальность

Изменение должно быть минимально достаточным для задачи.

Без прямой необходимости запрещено:

- выполнять сопутствующий рефакторинг;
- менять публичные контракты;
- переносить ответственность между пакетами;
- обновлять зависимости и tooling;
- менять порядок инициализации или завершения ресурсов;
- добавлять автоматический cleanup, migrations или deployment.

Перед удалением применяется
[Политика жизненности кода](./code-liveness-policy.md), перед новой
зависимостью — [Политика зависимостей](./dependencies-policy.md), перед
архитектурным изменением — [Архитектурная политика](./architecture.md).

## Контракты повышенного риска

Отдельной проверки требуют изменения:

- CLI command path, аргументов, defaults, help и потоков stdout/stderr;
- Arrow schema, framed protocol и границ payload;
- Flight actions, JSON fields, error codes и golden fixtures;
- checkpoint format, metadata и совместимости чтения;
- PostgreSQL schema, migrations и транзакционных переходов job state;
- разделения данных между PostgreSQL, `/tmp/transformer`, `recovery/` и
  `models/`;
- authentication, TLS/mTLS, process groups и shutdown semantics;
- optimizer, scheduler, early stopping и порядка обхода training payload.

Если контракт меняется намеренно, код, тесты и его источник правды обновляются
в одном change set.

## Проверки

Сначала запускаются самые узкие относящиеся к правке тесты, затем более широкие
проверки в зависимости от риска.

Базовый полный запуск:

```bash
python3.11 -m ruff check .
python3.11 -m pytest -q
git diff --check
```

Если среда проекта использует virtual environment, допустим эквивалентный
Python из него. Проверка считается пройденной только после успешного запуска.

Изменения PostgreSQL дополнительно проверяются на отдельной test schema.
Изменения CLI проверяются фактическим вызовом `--help` или `--version`.
Изменения deployment-конфигурации проверяются целевой системной утилитой, если
она доступна.

## Качество реализации

- валидировать внешние данные на границе;
- использовать type hints там, где они проясняют контракт;
- явно закрывать файлы, database sessions, engines, threads и subprocesses;
- сохранять атомарность публикации файлов и транзакций;
- не скрывать ошибку среды изменением production-кода;
- не заявлять о проверке, которая не была выполнена.

Проблема окружения не является основанием ослаблять тест, отключать validation
или добавлять fallback в production-код.
