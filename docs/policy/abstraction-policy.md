# Политика выделения абстракций

> Тип: политика. Этот документ задаёт правила выделения переиспользуемого кода.

Абстракция должна выражать устойчивую ответственность, а не только уменьшать
число повторяющихся строк.

Выделение оправдано, когда логика:

- используется в нескольких production-сценариях;
- содержит самостоятельный инвариант;
- изолирует внешний формат или инфраструктурную границу;
- достаточно сложна для отдельного тестирования;
- делает текущий код проще без сокрытия важных различий.

Сам факт похожести двух фрагментов недостаточен.

## Практическое правило

- одно использование — обычно оставить локально;
- два использования — проверить, действительно ли концепция общая;
- повторяющаяся устойчивая концепция — рассмотреть выделение.

## Допустимые примеры

- общий parser и validation environment-параметров;
- атомарная файловая публикация с `fsync` и `os.replace`;
- единая проверка Arrow schema или Flight action document;
- общий checkpoint reader для поддерживаемых форматов;
- отдельный adapter для PostgreSQL, filesystem или subprocess boundary.

## Недопустимые примеры

- новый `utils.py` ради одной короткой функции;
- wrapper над стандартной библиотекой без дополнительного контракта;
- общий helper для двух внешне похожих, но семантически разных payload;
- interface или factory «на будущее» без текущего использующего кода;
- перенос логики из понятного package в generic `common` или `helpers`.

Существующий `app/utils.py` не является разрешением помещать туда любую
совместно используемую функцию. Новая логика должна иметь связную
ответственность и по возможности жить в профильном package.

При выделении абстракции нужно сохранить наблюдаемое поведение и добавить тест
на её контракт, а не на внутреннее устройство.
