# Управление токенами доступа

> Тип: операционное руководство. Выпуск, передача, замена и отзыв Bearer-токенов.

Токен позволяет клиенту обращаться к Transformer. Здесь описаны команды для
работы с токенами и проверка результата. Формат, хранение и поведение кеша
описаны в [справочнике аутентификации](../authentication.md), заголовок RPC —
в [спецификации Flight](../../app/contracts/flight/v24/README.md).

Все токены представляют одного владельца — `inventory`. Это техническое имя;
клиентами могут быть и другие контролируемые системы. Несколько токенов удобны
для замены или передачи разным клиентам, но дают доступ к одним и тем же
заданиям и моделям. Соответствие `Token ID` конкретному клиенту оператор
учитывает отдельно от Transformer.

## Предварительные условия

- Команды выполняются из корня репозитория через `.venv` проекта.
- CLI должен обращаться к той же базе PostgreSQL, что и сервис Flight;
  схема должна быть обновлена по [руководству миграций](database-migrations.md).
- До выпуска токена подготовьте хранилище секретов и защищённый канал его
  передачи клиенту.

## Выпустить токен

```bash
./.venv/bin/python ./app/main.py auth tokens issue
```

Команда выпускает токен ровно на 180 суток (`180 × 24` часа) и выводит:

```text
Token ID: <UUID>
Expires: <ISO-8601 timestamp>
Token: a.<base64url>
```

`Token` — значение для Bearer-аутентификации. Transformer показывает его
только здесь и сохраняет в PostgreSQL только SHA-256. Если токен потерян,
восстановить его из БД или повторно вывести нельзя: выпустите новый и отзовите
потерянный по `Token ID`.

`Token ID` нужен для просмотра и отзыва; сам по себе он не даёт доступа.
Новый токен принимается при первом обращении без перезапуска сервиса.

## Передать токен клиенту

Передайте значение `Token`, а не `Token ID`, через принятый защищённый канал
и сохраните его в хранилище секретов клиента. Не помещайте токен в репозиторий,
историю команд, аргументы командной строки, логи или `.env` сервера.

Клиент предъявляет токен в каждом RPC:

```text
authorization: Bearer a.<base64url>
```

В недоверенной сети используйте TLS с проверкой подлинности сервера. Любой,
кто знает значение токена, может действовать от имени `inventory` до истечения
срока или отзыва с учётом задержки проверки кеша.

## Просмотреть токены

```bash
./.venv/bin/python ./app/main.py auth tokens list
```

Команда не раскрывает сами токены и показывает колонки `ID`, `Status`,
`Last used` и `Expires`. Возможны состояния `Active` и `Expired`; до
первого использования `Last used` имеет значение `Never`.

`Last used` отражает последнюю проверку токена в PostgreSQL, а не каждый RPC,
и может отставать от последнего обращения максимум на 60 секунд. Это
операционный индикатор, а не журнал всех запросов.

## Заменить токен

1. Выпустите новый токен командой `auth tokens issue`.
2. Сохраните и передайте новый `Token` клиенту.
3. Переключите клиент на новый токен и проверьте успешный RPC.
   `auth tokens list` может дополнительно показать обновлённый `Last used`.
4. Отзовите прежний токен по сохранённому `Token ID`.

Во время замены оба токена представляют `inventory`, поэтому клиент сохраняет
доступ к тем же заданиям и моделям. Завершите замену до `Expires` прежнего токена.

## Отозвать токен

При необходимости сначала найдите ID токена:

```bash
./.venv/bin/python ./app/main.py auth tokens list
```

Затем передайте UUID из колонки `ID`:

```bash
./.venv/bin/python ./app/main.py auth tokens revoke <TOKEN_ID>
```

Успешный `revoke` физически удаляет строку из PostgreSQL. Она сразу исчезает
из `auth tokens list`. Повторный отзыв и неизвестный ID возвращают `not found`:
удалённый и никогда не существовавший ID неразличимы.

Сохранённый в кеше процесса результат может разрешать отозванный токен ещё
максимум 60 секунд. Уже разрешённый потоковый RPC не прерывается. Для обычного
отзыва перезапуск сервиса не требуется.

## Истечение срока

После `Expires` новые RPC с токеном отклоняются. Истёкшая строка не удаляется
автоматически: она остаётся со статусом `Expired`, пока оператор явно не
выполнит `auth tokens revoke <TOKEN_ID>`.

Чтобы избежать перерыва, подключите новый токен до истечения прежнего,
проверьте RPC и затем отзовите прежний токен.

## Проверить выпуск и отзыв

1. Выпустите токен и сохраните отдельно `Token ID` и `Token`.
2. Выполните новый Flight RPC с выданным Bearer-токеном.
3. Убедитесь через `auth tokens list`, что строка присутствует и `Last used`
   перестал быть `Never`.
4. Выполните `auth tokens revoke <TOKEN_ID>`.
5. Убедитесь, что строка исчезла из `auth tokens list`.
6. После окончания 60-секундного интервала кеша убедитесь, что новый RPC с
   отозванным токеном завершается как `UNAUTHENTICATED`.

Повторный отзыв в этом сценарии должен завершиться ошибкой `not found`.
